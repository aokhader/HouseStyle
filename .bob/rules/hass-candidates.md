# home-assistant/core — candidates and incidents

Patterns that did not clear the support threshold, plus one-off corrections deliberately kept out of the promoted set.

## Candidates (support below 3)

- `hass-r030` **[api-design]** A domain's triggers.yaml, conditions.yaml and services.yaml must describe the full surface the implementation accepts - every field the schema takes, including the common `for` duration, and every domain the feature applies to, including the matching input_* helper domains - and a refactor may add entries but must never drop or rename existing ones. — support 2 (#166484, #165378)
- `hass-r032` **[api-design]** A light must preserve its last brightness: async_turn_on may only default to full brightness for a bare turn-on with no attributes and must keep the current level when the call supplies only effect or colour, and async_turn_off must not zero or clear the brightness attribute. — support 2 (#170841, #161841)
- `hass-r038` **[api-design]** Collections surfaced to the frontend (select options, websocket payloads) must be ordered deterministically, e.g. sorted, rather than inheriting dict or matcher load order. — support 2 (#169403, #169387)
- `hass-r042` **[api-design]** Create shared clients, sessions and derived per-entry values once in async_setup_entry, store them on entry.runtime_data and close them in async_unload_entry; platform modules and entities must consume that object rather than constructing or re-deriving their own copy. — support 2 (#175902, #169745)
- `hass-r074` **[api-design]** Resolve the config entry a service call targets with homeassistant.helpers.service.async_get_config_entry rather than hand-rolled lookups, so a missing, wrong-domain or unloaded entry raises ServiceValidationError instead of a generic or unhandled error. — support 2 (#175472, #159603)
- `hass-r076` **[api-design]** Sensor entity descriptions must set suggested_display_precision explicitly, alongside the native and suggested units, instead of relying on the device-class default. — support 2 (#172464, #160392)
- `hass-r094` **[commit-hygiene]** A change that alters behaviour users may already depend on - including rerouting an existing device or event action to a different action type - must be declared as a breaking change in the PR description and release notes, even when it is the intended bug fix. — support 2 (#172634, #158533)
- `hass-r096` **[commit-hygiene]** Keep a pull request to one purpose: a dependency-bump PR must contain only the changes the version update requires, and a user-visible bug fix must land as its own minimal change so it can be cherry-picked into a patch release, with new entities, fixtures, snapshots and refactors moved to a follow-up. — support 2 (#176439, #165198)
- `hass-r110` **[correctness]** An entity registry snapshot whose 'aliases' field renders as list([None]) must be investigated as an entity-registration bug; aliases must be an empty set or a set of non-null strings. — support 2 (#173411, #172831)
- `hass-r112` **[correctness]** async_turn_on must never leave the device off: a zero percentage or brightness must be clamped to the minimum running value or treated as if it had not been supplied so the default applies, rather than mapped onto the device's off state. — support 2 (#172736, #169778)
- `hass-r118` **[correctness]** Create entities only for the capabilities and datapoints the specific device instance actually reports, and gate each conditional entity on the very flag or data key that supplies its value - not on a static definition table or an unrelated feature flag. — support 2 (#168051, #161527)
- `hass-r119` **[correctness]** Custom pylint checkers must key on the exact AST shape they target: handle the keyword form (service_func=) as well as the positional argument, and inspect the argument node type rather than merely counting arguments. — support 2 (#171453, #170652)
- `hass-r125` **[correctness]** Do not silence a typing error with a blanket `# type: ignore`; give the value the correct type instead - cast it explicitly, build a properly typed structure, or add typing for the library function. — support 2 (#167602, #164654)
- `hass-r132` **[correctness]** Error and warning messages raised by integrations that can have multiple config entries or devices must identify the failing entry or device by title, host, entry_id or device name. — support 2 (#172276, #165924)
- `hass-r139` **[correctness]** Key long-lived caches and lookup dictionaries by a stable identifier such as the unique_id, never by a value that changes at runtime such as the entity's display name or its entity_id. — support 2 (#172264, #160860)
- `hass-r140` **[correctness]** Log expected and per-item failures at debug or warning level, never at warning-in-a-loop or _LOGGER.exception; reserve the higher levels for conditions the user can act on that cannot repeat once per polled item. — support 2 (#171589, #160953)
- `hass-r144` **[correctness]** Normalize a device- or payload-supplied unit before it reaches the entity: map it onto Home Assistant's canonical units for the entity's device_class, fall back to the entity description's default when it is unrecognized, and turn an empty string into None rather than passing it through. — support 2 (#171588, #168527)
- `hass-r145` **[correctness]** Normalize every MAC or Bluetooth address with homeassistant.helpers.device_registry.format_mac before using it as a config entry unique id, a device identifier, or a device registry connection; never hand-roll upper/lowercasing or colon insertion. — support 2 (#165472, #163936)
- `hass-r164` **[docs]** An exception translation key must be written for the specific failure that raises it: do not reuse one key across unrelated exception types or borrow a service/action key for the coordinator update path - split or broaden the key instead, and pass the underlying error text as its placeholder rather than a hardcoded generic string. — support 2 (#171744, #170445)
- `hass-r169` **[docs]** Polling and update-interval constants must match the cadence stated in the integration's README, inline comments and the PR description; change the constant or the documentation so they agree. — support 2 (#167371, #161722)
- `hass-r195` **[providers]** A legacy YAML platform reduced to an import or repair-issue stub must still report successful setup - return a no-op service or True rather than None - so the legacy platform helper does not log a setup failure. — support 2 (#167308, #166838)
- `hass-r197` **[providers]** Do not feature-detect on the integration's own pinned library with hasattr/getattr/callable: the manifest pins the version, so call the API directly and unconditionally - including registering update listeners in async_added_to_hass through async_on_remove. — support 2 (#174851, #163893)
- `hass-r198` **[providers]** Encode device values through the semantics the pinned library declares - its enum members and its documented units - never through magic integers, divisors or thresholds written into integration code. — support 2 (#176610, #170729)
- `hass-r204` **[providers]** manifest.json requirements must match what the code actually needs: every third-party module the integration imports has to be declared, and the pinned version must be new enough to provide every attribute and method the code calls - bump the pin in the same PR. — support 2 (#172186, #160409)
- `hass-r207` **[security]** Diagnostics must redact every identifying field the payload can contain - MAC addresses, serials and device identifiers as well as credentials - and must redact them everywhere they appear, including nested structures such as override target ids, not only in the collection that primarily lists them. — support 2 (#176514, #173481)
- `hass-r209` **[testing]** A mock or fixture must configure every library call and accessor the exercised path touches - including calls whose exceptions the integration suppresses, and the availability accessor the base entity reads - matching the fixture combination the integration's existing tests already use. — support 2 (#165647, #162110)
- `hass-r211` **[testing]** A test covering a translated error must assert the exception's translation_domain and translation_key rather than merely that a HomeAssistantError was raised, and a platform that gains such a raise must gain the matching failure test. — support 2 (#168559, #163685)
- `hass-r213` **[testing]** Advance coordinator intervals with the freezer - freezer.tick(...) followed by async_fire_time_changed(hass) - rather than a separately computed dt_util.utcnow() + timedelta timestamp, and never one captured before the config entries were set up. — support 2 (#166686, #163923)
- `hass-r224` **[testing]** Do not write generated entity_ids into tests by hand: resolve the entity through the entity registry by unique_id or config entry and assert on the resolved id, including when asserting that an entity was not created. — support 2 (#168105, #168022)
- `hass-r226` **[testing]** Drive and inspect an integration through its public test helpers and registries - inject_bluetooth_service_info, the entity registry - never through private coordinator callbacks or internal hass.data structures. — support 2 (#170432, #167393)
- `hass-r229` **[testing]** Entity-platform tests must pin the exact set of entities a setup produces - snapshot them, or assert the precise expected entities per affected device type - never a smoke check that setup did not crash or a `>=` lower bound. — support 2 (#165241, #160409)
- `hass-r247` **[testing]** Shared mock/data construction repeated across tests belongs in a pytest fixture in conftest.py, not in module-level builder functions each test calls manually. — support 2 (#171182, #170932)
- `hass-r259` **[testing]** When shared code gains a branch, add coverage for every consumer of it, not only the one the change was written for - each flow that calls a shared config-flow helper including reauth, and each subclass of a modified trigger or helper base class, including subclasses whose semantics the change would alter. — support 2 (#169660, #168224)
- `hass-r028` **[api-design]** A config flow must validate the connection by calling the same third-party library client the coordinator uses; it must not re-implement API paths, endpoints or response parsing inline. — support 1 (#175085)
- `hass-r029` **[api-design]** A configuration entity whose value can be changed outside Home Assistant and receives no push updates must be disabled by default and set _attr_should_poll with a long SCAN_INTERVAL, mirroring the existing pattern in the integration. — support 1 (#169603)
